# 功能设计决策轮（Feature Design Round）

## 定位

把一次模糊想法收敛成“主目标 + 边界”，产出 2-3 套可比较的候选方案 + 角色评审打分 + 决策材料，供用户拍板。**本轮不写业务实现代码**；探索代码只读。明确不适用：纯 bug 修复、单文件小改、用户已明确指定实现的改动。

## 流程

1. **澄清主目标**：先收敛最重要的分叉，一次只问关键的 1-3 个问题。典型分叉：范围（只做本市场，还是需要跨市场联动）、时效（收盘复盘 / 盘中 / 都要）、形态（独立页 / 现有页面加卡片 / 都要）。产出：一句主目标 + 显式边界（如“本期不做 X，架构留口”）。
2. **产出候选方案**：按 2-3 个互补切面推进（数据层 / 页面 IA / 可行性调研）。方案必须基于现有仓库模式（多数据源 fallback、缓存策略、组件形态），并落到 `docs/design-rounds/YYYY-MM-DD-<主题>/`。
3. **评审打分**：依次按三种角色视角评审，每套方案都要有分维度评分、推荐和理由：
   - `ux-reviewer`（体验官）：交互、易用性、信息密度
   - `genz-reviewer`（年轻用户口味）：移动端、现代观感、话题感
   - `pro-investor-reviewer`（专业投资视角）：是否真正有利于投资分析决策
   若用户明确要求并行评审且当前环境允许派子代理，可按角色派发子代理；否则由主会话依次从各视角执行评审。不要擅自后台并行。
4. **汇成决策材料**：把“候选方案 + 评分 + 权衡”写成决策页。沿用仓库既有模式：`docs/design-rounds/<主题>/decision-brief.html`（+ 本地预览版可另存 preview）。给用户链接或打开文件，等用户拍板；用户有权合并各方案优点。
5. **落定后转实施**：用户选定后，若需要实施计划，用仓库既有 `docs/superpowers/plans/YYYY-MM-DD-<主题>.md` 惯例产出计划；实施遵循 TDD 与既有契约测试，不属本轮。

## 红线

- 决策轮只交付方案与评估，不写业务代码。
- 调研发现接口/数据源不可行时如实上报并降级/改范围，不硬造可行。
- 评审结论是参考打分，最终决策权在用户。
- 每轮产物留档于 `docs/design-rounds/`，可追溯。

## 常见问题

- 未澄清范围/时效就开始设计：先收敛主目标再推进。
- 方案同质化：各设计线从不同切面出发（数据层 / 页面 / 可行性）。
- 跳过评审直接给用户看：评分是决策轮的信任来源。
- 把评审结论当“通过/否决”：它只是参考。
